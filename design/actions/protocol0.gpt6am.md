# Typed selected work alongside immutable physical observation

## Recommendation

Start with **caller-supplied typed production and installation**, integrated at an
ordered driver's immediate-batch/finish boundary. Keep the current physical
`Action` and `Visitor` intact. Add a small owned desired-file request, explicit
target claim, satisfaction policy and pending-work envelope. A generated request
does not need a fake source file, another disposition enum, or a global registry.

Use explicit desired-input/provider admission when generated **directories and
their children must participate in discovery**, not merely because a summary file
is generated. Open descriptor dispatch is an optional application binding for
heterogeneous operations; it does not solve input admission or publication.

This recommends a mechanism, not a default generated equality rule, mapping
winner, or JW copy scope. Those choices remain visible below.

Consequently an enum extension alone fails at **four** points: no generated input
slot, no legitimate physical facts, no clean-work yield, and no generated byte
source in the installer. The implementation seam is the public immediate inspector
plus an ordered composition, not a mutation hidden inside `Visitor::late`.

## Separate observations, attributes, desired facts and selection

**Observation** means a physical fact acquired by the observer at a named binding:
presence, kind, metadata, literal link, or an explicitly requested content
comparison result. Its lifetime is an assessment, not a permanent certificate.
`None` on an observed side means genuine absence; excluded and unknown differ.
Keep baseline physical comparison unchanged even when generated work is selected.

**Domain attributes** are caller-typed annotations such as `Class::Report`,
`RepositoryRegion::Administrative` or `SummaryLabel("A")`. Their owner is the
classifier/configuration that supplied them. They are not `Metadata`, absence,
or permission to replace a target. An externally acquired domain fact needs its
own provenance/input binding; a visitor cannot acquire it through hidden I/O.
Freeze needed attributes before speculative assessment, or provide them later as
an accepted child result to the ordered driver.

**Desired facts** describe the intended result: generated regular-file bytes,
required mode, literal link text, or a recipe and frozen inputs that determine
them. Desired mode is an instruction/constraint, not an observed source mode.
Only explicitly specified attributes participate; do not invent a source mtime.

**Selected work** records the operation, parameters, destination and dependencies
chosen after policy and validation. Keeping a physically different file does not
make it equal. Producing a summary does not mean it was installed. Satisfied,
deliberately retained and skipped-incomplete are distinct outcomes, even if all
three perform no write.

## Three protocol options

### 1. Narrow producer + installer, or caller-typed operations — recommended first

The caller reserves generated destinations, assesses physical inputs, folds
accepted results, and produces `DesiredFile`. A generated installer observes the
actual destination, evaluates the chosen satisfaction rule, and installs if
selected. Its executor uses staging/attribute semantics, not a temporary fake
source tree passed through the physical comparer.

The physical plan and generated requests enter one conflict/dependency boundary
**before either receives effect authority**. For a postorder summary the body is
unknown initially but its destination can be reserved initially. That reservation
prevents mirror removal/copy from also claiming the output. The finish phase fills
the request's body after children complete.

One compiled application can use `enum Job { Physical(...), InstallReport(...) }`
or generic `Job<P>` and a `match`. Parameters remain typed. This supports an
ordinary physical tree plus a few generated leaves with very little new core
surface. A producer invoked only after exhausting the old walk can work for a
disjoint output sink; it cannot alone coordinate in-tree ownership and dependencies.

### 2. Explicit desired-input/provider admission

Admit a separate desired namespace before assessment:

```text
desired candidates = physical candidates + generated candidates
                  → resolve logical ownership and target claims
                  → observe actual target at routed coordinates
                  → assess desired/target satisfaction
                  → finalize work and children
```

These are **not** injected `Name`/`Facts` values. A candidate has an origin
`Physical(binding)` or `Generated(recipe/bytes)` and explicit desired shape.
Physical source absence remains physical source absence. A generated input can
exist even when both physical listings lack its name.

A minimal provider needs `list_children(context) -> candidates` and an input
resolver/producer, with a declared enumeration completeness scope. A list of two
generated files is not authority to prune every unlisted target. Dynamic provider
state must be frozen, persisted, or reconstructible for pause. Provider I/O runs
as inspection/production, not inside pure callbacks.

This earns its cost for virtual directories, merged source trees and mapped
subtrees whose child discovery belongs to the desired model. It also requires
logical collision resolution, explicit target probing and a desired-tree child
model. Do not introduce it just to emit `summary.txt` after a physical traversal.

### 3. Extensible descriptor/handler mechanism

An application may need jobs from independently versioned producers or stored
continuations whose operation family is not fixed in one Rust enum. Then use an
owned `{ kind, version, payload }` descriptor, bound explicitly to a handler.
The current cursor's `directory-summary/v1` is a concrete narrow precedent.

The handler decodes and validates payload, declares target/read dependencies,
produces typed desired data or executes the declared operation, and defines any
saved state. The scheduler must see target claims and dependency position; an
opaque payload cannot conceal arbitrary writes while claiming sibling independence.
Reject an unknown kind/version before effects for the affected finalized unit.
Binding can be a supplied dispatcher function or finite map; global discovery is
unnecessary. Executable code, closures and native runtime resources are rebound,
not serialized in the descriptor.

Descriptors solve **representation/dispatch extensibility**. They do not resolve
physical/generated conflicts, prove target satisfaction, or fix clean-plan loss.
Use typed payloads for known jobs; permit an open payload only at a real extension
boundary. An ordered stateful native operation belongs here or in a typed executor,
never as a speculative visitor callback.

## Smallest implementable data and interface boundaries

The following is schematic Rust, not a proposed exact public signature or a new
core serialization dependency. `P`, `A`, `C` and `R` are caller-owned types.

```rust
struct Target { root: RootId, relative: NativeRelativePath }
struct DesiredFile<P> {
    logical: LogicalId,
    target: Target,
    content: Content<P>,
    attributes: DesiredFileAttributes,
    satisfaction: SatisfactionRule,
}
enum Content<P> { Bytes(Vec<u8>), Recipe(P) }
enum Satisfaction { Satisfied, Unsatisfied, Unknown }

struct Child<C> {
    logical: LogicalId,
    source: Option<PhysicalBinding>,
    target: Target,
    context: C,
}
struct Selected<A, C, R> {
    before_children: Vec<A>,
    children: Vec<Child<C>>,
    finish: R,
}
```

`Target` is an intended route: it never asserts that a target exists. A child may
also require an explicit actual-target inspection binding, including absence or
private preparation. Keep that separate from final logical coordinates. Do not
reuse `source: None` to mean a generated source; a provider-based child needs an
explicit generated origin variant. For the narrow composition generated files
remain finish requests, not invented physical children.

The composition has four useful callable boundaries, which can initially be plain
functions rather than traits:

1. **Plan:** immutable inspected physical batch + frozen attributes/context →
   selected local work/child contexts/finish recipe. Pure; no accumulated mutable
   callback state. Borrow `DirectoryPlan` during planning rather than serialize it.
2. **Validate claims:** selected physical and generated work + binding/ownership
   policy → validated unit or conflict. Claims cover target replacement subtrees
   as well as leaf writes, and reservations for later finish work.
3. **Produce and assess:** a ready recipe + accepted aggregate → desired bytes;
   read-only target observation/content comparison → satisfaction. This is an
   explicit driver task, not hidden I/O in `Plan` or a `Visitor` accessor.
4. **Execute:** validated pending action + rebound runtime → success/error.
   Installer owns byte writing and requested attributes; driver owns advancement,
   child release, folding and finish. A pure finish reducer can instead return a
   logical value to an output consumer without selecting filesystem installation.

`finish: R` represents a known obligation that can generate actions after child
results; it is not a promise that all output bytes are available at parent
inspection. For a fixed finite application an `Option<SummaryRecipe>` is enough.
Child context is immutable inherited/replaced policy and routing data, not mutable
parent references. Keep aggregate state in driver frames, passing its accepted
value to finish. There is no need to encode before/children/after as a general DAG
until a real cross-subtree dependency requires it.

## Clean physical inputs with selected work: complete trace

Bind two identical empty directories and request a root summary at
`output-root/summary.txt`. Physical immediate inspection returns an empty diff.

1. The binding supplies the output request independently of physical union names.
2. The composition reserves its destination and selects a root finish obligation.
3. The immediate assessment is accepted by the ordered driver even though clean.
   No call to divergence-only `PlanWalk::next()` is relied on to carry this work.
4. With no children, finish produces bytes and probes the actual output target.
5. Satisfaction policy either proves no write necessary or selects installation.
6. The installer settles; only then is installation-required completion closed.
   A value-only consumer instead receives the produced bytes, with delivery a
   separate result.

For nonempty roots, parent `before_children` obligations gate dependent child
admission; finish waits for child aggregates. A paired directory can have an empty
physical diff and still need these gates. Publication must retain a pending
work/control envelope whenever there is **selected local work, reserved finish,
or an unresolved child dependency**, independently of `diff.is_empty()`.
Observation-only clean batches still advance and contribute coverage.

The smallest implementation is a sequential driver consuming `inspect_directory`
directly, preserving existing comparison behavior. If extending the current rich
walk/frontier instead, change plan retention, yield/control events, divergence
seals and clean-child admission together. Keep `changed_dirs` and divergence
counts tied to baseline physical differences; use separate work outcomes. Merely
changing `changed.then_some(plan)` to include `work()` misses finish obligations
and the downstream yield and seal predicates.

## Target satisfaction and a changed parameter

Example: `Summary { label: "A", counts: 3 }` produced the installed report. Change
only `label` to `"B"`; physical source/target inputs are untouched. The old
physical comparison still says equal. Generated satisfaction must evaluate the
new desired content, rather than conclude no work from that physical result.

| Explicit mechanism | Result and tradeoff in this example |
| --- | --- |
| Always install | B is written each run. Simple, but no generated equality/no-op claim; selecting work is unconditional policy. |
| Exact desired-byte comparison | Render B and read current target; A differs, B installs. Rerun B can no-op if required kind/attributes also match. Parameter change yielding identical bytes need not rewrite. |
| Content digest comparison | Digest desired and actual bytes under a specified algorithm/domain, also check kind/attributes. Can avoid retaining both bodies, not inherently avoid reading target. A stored desired digest alone proves nothing about current target bytes. |
| Recipe/input identity plus validated receipt | Identity includes output-affecting parameters, producer version and frozen input identity. Changed label invalidates prior identity. Requires a declared trusted association with current target content; a stale sidecar alone is insufficient. More persistent state than the first slice needs. |

Keep `Unknown` explicit when evidence is insufficient. The caller must choose
additional observation, conservative installation, or deferral/refusal. It cannot
silently convert Unknown to Satisfied. Target kind and requested attributes are
part of satisfaction; equal bytes in a symlink or wrong-mode file are not enough.
Generated leaf over directory additionally requires existing coupled replacement
and descendant-preservation authority; bytes do not authorize its removal.

No default is selected here. For a first discriminator use **explicit exact-byte
comparison** because it visibly distinguishes changed parameters and a real no-op.
That is a fixture choice, not a product default. Nondeterministic recipes require
retaining produced bytes or an immutable output reference when pausing after
production; simply rerunning a clock-dependent recipe changes the desired input.

## Collision and output-placement discriminators

### Physical `summary.txt` and generated `summary.txt`

`source/summary.txt = "authored"`, generated logical summary = `"count: 3"`, both
route to `target/summary.txt`. There are two desired owners, not one physical file
whose metadata can be overwritten in the plan. Explicit choices are:

- Refuse ambiguous ownership before either install/removal is authorized.
- Reserve that name for generated output, excluding it from physical transfer
  and (if intended) summary input; diagnose/accept the authored-name conflict
  according to declared policy.
- Retain the physical candidate and suppress generated installation, reporting
  that suppression rather than reporting generated satisfaction.
- Route the generated output elsewhere, e.g. `reports/summary.txt`.

An **existing target** at a generated-owned destination is not automatically an
ownership conflict: it may be the previous generated result to reconcile. A
physical source candidate or physical target-only removal claim competing for
that target is a conflict. A pair-wide reservation implemented with early
preservation only removes the physical engine's authority; the output component
still needs separately declared authority. Ordinary user protection of a subtree
must not be reinterpreted as permission for a generated component to overwrite it.

### Two logical inputs, one target

`a/report -> out/report` and `b/report -> out/report` collide even when logical
names sort apart. Choices: refuse; choose a declared priority owner; explicitly
coalesce identical desired outputs/attributes; or merge both inputs with one
producer so that there is one writer. Native-name enumeration order must never
accidentally select the winner. Coalescing needs actual desired equivalence, not
equal recipe kind alone. Also detect `out/x` as a leaf writer versus `out/x/y`.

For arbitrary mappings, directory-local validation cannot discover all conflicts
before earlier effects. Either predeclare/validate the complete relevant target
claim set, constrain mappings to disjoint owned subtrees, or retain a routing
claim index with clearly documented late-conflict failure. That index tracks
ownership, not effects history. The smallest initial contract accepts only
predeclared output destinations in reserved/disjoint regions; broader mapping
semantics remain a choice, not a hidden implementation assumption.

### Same-tree summary versus separate output root

Separate output: compare `src`/`dst`, emit to `reports/<logical>/summary.txt`.
Reserve `reports` as disjoint from both input roots and validate output mappings.
The summary measures assessed input facts; it need not claim post-sync equality.

Same-tree output: write `dst/summary.txt`. On the next run it is physically
target-only unless the source also has it, and ordinary mirror could remove it.
Moreover including it in the counts changes the next summary. Choose explicitly:

1. Reserved/excluded output namespace: observe real presence when needed for
   installation, but exclude output names from the summary's input domain and
   physical transfer/deletion. Report that domain scope.
2. Include previous output as input: capture its observation before installation,
   and define the report as a snapshot including the previous report. This may
   not converge and is not a fixed-point algorithm.
3. Separate read and output phases with an explicitly defined input manifest,
   still specifying whether old generated files belong to that manifest.

If a parent summary includes child **generated results**, fold their logical
values directly rather than rediscover their newly installed files. This is a
dependency on accepted child output, distinct from physical observation. If it
instead promises a post-effect physical inventory, schedule an explicit new
observation; pre-effect counts cannot support that claim. None of these options
select JW's ignored-file breadth or target-only deletion policy.

## Continuation, rebinding and publication

Serialize owned future state only: lossless logical/target coordinates, root
binding identities, selected typed operations or versioned descriptors, frozen
parameters and necessary attributes, recipe inputs or produced body/reference,
target-claim scope, child contexts/order/position, aggregate and incomplete state,
and pending before/children/finish/publication phase. Persist the selected
satisfaction rule. A recipe identity must cover output-affecting inputs, not just
the handler's name. Changing parameters in an existing continuation requires an
explicit invalidation/replanning rule; otherwise reject it or start a new run.

Rebind root resources, producer/installer implementations, content stores and
runtime facilities. Validate descriptor versions, native path encoding, routing
constraints and phase/dependency invariants before dispatch. `std::fs::Metadata`,
borrowed dirents, open streams, closures, staging handles and permission scopes
are not continuation DTOs. Reobserve unresolved targets when needed; saved
physical observations are not renewed authorization by deserialization.

Pause between joined units. A body already produced but not yet installed is
pending work, so retaining it is legitimate future state, not an effects ledger.
Alternatively retain reproducible inputs and regenerate. A failure offers no
effects history, rollback or recovery guarantee; retry must reassess actual
unresolved state. Skipping an installation obligation marks its completion
incomplete, not satisfied. No completed-effect catalog is required.

Keep three publication events distinct: accepting a work/control envelope,
producing a logical output value, and completing selected filesystem installation
or external delivery. An installation-required frame cannot fold as successfully
closed while its install is pending. A value-only assessment can close before
external delivery, as long as that contract is explicit. Cursor save and external
output are not one transaction; reuse/loss can repeat or lose delivery. The
existing cursor README documents that limitation; a descriptor does not fix it.

## Candidate downstream probes and remaining decisions

These are proposed focused probes, not results of tests run in this study.

1. **Generated admission/publication:** two empty equal roots, one root finish
   report. Assert physical diff remains empty and exactly one selected install
   reaches the bound executor. Add a clean paired child and assert parent
   prerequisite work settles before dependent child execution.
2. **Satisfaction:** explicit byte mode, label A then B then B. Assert first/second
   writes, third proven no-op; repeat with equal bytes but wrong required mode.
3. **Ownership:** authored/generated same name and two logical-to-one target
   mappings. Exercise explicit refusal before conflicting writes; separately
   test a declared generated reservation without treating the old target as a
   second desired owner. Include leaf/ancestor conflict and protected subtree.
4. **Finish dependency:** create container, run two child jobs, produce summary
   from their accepted aggregate, install, then close. Pause with finish pending;
   rebind dispatcher and retain identical parameters/bytes. No callback effects.
5. **Output domain:** run same-tree reserved report twice and compare report
   inputs with disjoint-output composition. Confirm the chosen scope avoids
   self-counting and target-only mirror removal; keep physical presence truthful.
6. **Descriptor extension only if needed:** round-trip one typed report job and
   one application-specific payload; reject unknown version and undeclared target
   claims. This tests binding extensibility without implementing global discovery.

The real forks are generated equality/default evidence cost; logical/target
collision policy and routing breadth; output inclusion/domain; recipe stability
and retained-body strategy; and whether virtual child discovery justifies a
provider. Finer effect pause machinery belongs to the execution-model work.
Broader JW copy policy belongs to its native/transfer owners. The narrow protocol
can be implemented and tested while all these product choices remain explicit.
