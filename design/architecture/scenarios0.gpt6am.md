# Three component compositions

The architecture joins **tree inspection, work selection, progression and output
execution** without giving any one of them ownership of all four. A directory
copy composes these directly. Workspace creation places the composition inside a
JJ-owned lifecycle. A resumable assessment composes inspection with a different
progression driver and a generated-output consumer.

These are proposed architectural scenarios, with implemented routes identified
explicitly. The source was read from diff-dirs parent `013bec8a` (production source
unchanged since `c7b86ffb`) and JW working-copy coordinate `a5976406`. The withheld
parent statement, full roadmap and other same-wave outputs were not consulted.

## Common component boundaries

| Component | Input → output | Owner and progression responsibility |
| --- | --- | --- |
| Binding | Source/target coordinates and options → validated roots | Caller chooses roots; library validates its filesystem binding. JJ identity is outside this binding. |
| Immediate inspector | Present directory sides, logical coordinate, frozen visitor → immutable `DirectoryPlan` | Core owns listing handles and observations; each call finishes one immediate batch. |
| Work selector | Actual early/late facts → admission and legal actions | Caller supplies pure policy; core validates it. Selection does not execute effects. |
| Progression driver | Finalized batch plus active traversal state → next tip or completion | Driver owns pending descendants, ordering and pause boundaries. Its state is distinct from the observations it consumed. |
| Effect/output consumer | Authorized filesystem work or generated logical output → effect result or delivered output | Sync owns filesystem preparation/application; a generated-output consumer owns its separate delivery. |
| Optional continuation codec | Owned continuation data ↔ bytes | Codec preserves a position; runtime components interpret and validate that position. |

The existing inspector already accepts physical source/target directories
separately from logical roots and `dir` (`inspect_directory`, `visitor.rs:978`).
That permits staged physical destinations with final logical visitor paths. It
does **not** make the current applier an arbitrary path-mapping engine: its entry
executor derives children with `from.join(entry.name())` and
`to.join(entry.name())` (`apply.rs:434–460`).

Keep the premise simple: source contents are good; concurrency and locking are
out of band. Failure provides no rollback, recovery guarantee or effects history.
An operation may report partial progress without recording a replayable inventory.

## Scenario 1 — ordinary directory copying

### Assembly and inputs

A caller supplies source `S`, destination `T`, a byte-transfer choice, and an
explicit treatment of target-only contents. Neither tree needs repository
metadata. For a concrete copy scenario, `T` is absent and its parent exists; for
an update scenario, `T` is an existing directory with local extras to retain.

The implemented assembly is:

```text
caller roots/options
  → Applier binding
  → root dispatch / paired walker
  → immediate inspection + pure visitor + validation
  → sync application and its recursive one-sided inspection
  → report or partial failure
```

Use `Applier::new(S, T, CopyPolicy::Copy)?.run()` for the absent destination.
For existing destinations, ordinary copying must select its intent: the default
applier mirrors and removes target-only entries; `diff_dirs_sync::update` retains
target-only branches. These are different authorized operations, not an inferred
cleanup side effect of the word “copy.” Reflink policies change file transport,
not traversal or target-only authority.

### Progression

1. **Bind.** `Applier` owns canonical, nonoverlapping roots, transfer policy and
   visitor. Construction writes nothing. A source directory is required; a
   missing target is supported. Replacing a target root leaf needs the explicit
   replacing constructor (`sync/src/lib.rs:21–70`).
2. **Inspect the root or a directory pair.** Listing produces immutable union
   names and actual presence. Early preservation can stop a child before its
   metadata/readlink and before any descendant enumeration. Admitted entries
   gain facts and baseline actions; late selection can retain or redirect legal
   work. The entire immediate batch is validated before publication.
3. **Apply local work and continue.** Paired-directory descent belongs to
   `PlanWalk`. Source-only creation and target-only removal recurse inside sync.
   Both routes use the same visitor semantics. A source-only `assets/` causes
   container creation followed by inspection of its children; an existing
   paired `src/` becomes a pending paired child. The driver does not submit both
   routes for the same paired descent (`apply.rs:560–569`).
4. **Install bytes.** The sync kernel prepares regular files at the target side,
   applies its metadata contract and installs them; symlinks retain literal link
   text. The visitor never supplies effects or writes through a callback.
5. **Finish.** The report distinguishes observed differences, selected work and
   completed operations. Exhaustion under preservation policy does not mean
   full-root equality. On failure the caller can start fresh comparison; current
   `Applier::run` does not expose a serialized application continuation.

For a type collision, replacement remains coupled. A directory cannot be removed
to make room for a file if retained descendants require it. Conversely, a
leaf-to-directory replacement prepares the admitted source subtree privately
before replacing the old leaf. These local preparation rules are not a tree-wide
transaction (`apply.rs:490–669`).

### Information that saves work

The caller can preserve a known irrelevant subtree in early selection, saving
child observation, interior enumeration and effects. Late preservation saves
descent/effects after paying the immediate observation cost. A matched directory's
`comparison() == Some(false)` is only a container fact: it cannot prove its
children equal. Whole-subtree knowledge can authorize stopping descent, but no
mtime or inode hint supplies that proof automatically. A known list of source
leaves can instead use `seed_leaves`; that is an explicit-input transfer route,
not a demand to enumerate a tree merely to manufacture the same list.

The architecture therefore supports both discovery-led work and known-input work.
No JJ adapter, serialized cursor or general action registry is required for this
scenario.

## Scenario 2 — main JJ archive to a receiving workspace

### Assembly and ownership

Here **archive** means the primary checkout owning the JJ repository storage,
not a CAR/tar file or an ordinary registered receiving workspace. The scenario
binds that archive as donor. Current JW often takes `inventory.current_root()` as
the clone source; thus calling the existing path from the archive instantiates
this scenario, but the code does not enforce “always use archive” as a universal
source rule (`lifecycle.rs:690–711`). Alternate registered-workspace donors are
outside this scenario.

The command supplies archive root `A`, receiving path `W`, workspace name, desired
base `D`, copy options and desired Git colocation. The preferred product outcome
is colocation on by default with `--no-colocate` opt-out. That preference is not
the current default and does not prove combined CoW feasibility.

| Owner | Inputs → outputs |
| --- | --- |
| JW command adapter | Archive, destination, name, revision and mode options → native creation sequence, frozen tree-transfer inputs and managed record |
| JJ | Shared repository plus desired revision → registered workspace, its own checkout binding and native working-copy state |
| Native Git integration through JJ | Git-backed repository and supported colocation request → receiving `.git` linkage and linked-worktree administration |
| Generic transfer | Selected actual archive data and receiving roots → private copied/reflinked data, preserving native metadata boundaries |
| JW ownership adapter | Newly allocated Git registration and receiving workspace → `OwnedGitWorktree` provenance/marker |

The primary `.jj/repo` is a directory owning shared repository storage; receiving
workspaces use their native repository linkage. `WorkspaceInventory::load`
identifies the physical primary from repository ownership, not merely a workspace
named `default` (`workspace.rs:119–139`). The receiving `.jj/working_copy/checkout`
belongs to the new workspace. The private `tree_state` cache is a separate object
and may be adopted only through an explicitly native-aware route. Neither `.jj`
tree is an ordinary payload subtree to mirror wholesale.

For colocation, `.git` likewise belongs to native setup. The inspected ownership
adapter expects a distinct per-worktree Git directory and common directory,
checks reciprocal topology, and writes `jw-owner` only for a newly created
registration (`ownership.rs:36–65,98–119,241–289`). This scenario needs no assumption
about a universal physical location for the archive's Git object store: the
adapter asks JJ/Git. Copying the archive `.git` into `W` cannot create the required
receiving identity or registration.

### Existing executable compositions

**Native materialization, optionally colocated:** JW resolves creation inputs,
calls `jj workspace add --name … --revision D …`, and passes `--colocate` when
selected. Native creation supplies tracked contents. JW records the actual owned
Git registration for colocation, applies selected auxiliary payload and links,
and records managed metadata. Current `CreationMode` makes `Colocated` distinct
from `CopyOnWrite`; unset options mean CoW and JJ-only metadata
(`lifecycle.rs:126–152`).

**Existing CoW/JJ-only materialization:** JJ first creates a sparse-empty receiver.
JW obtains the donor's tracked leaves, clones those leaves, copies only donor
`tree_state`, validates with native `status`, then runs `restore` to the receiving
working-copy revision. Donor tree `S` may differ from desired tree `D`. The native
workspace checkout binding remains receiving-owned. Watchman or unsupported clone
conditions can select the existing ordinary-JJ fallback
(`workspace.rs:501–505,558–574,616–660`; `jj.rs:643–667`). The earlier
[state account](/design/execution/state0.gpt6a.md#5-jw-specifically-native-jj-state-and-the-adoption-test)
provides bounded adoption evidence; it is not evidence for colocation composition
or universal hash avoidance.

Those are implemented compositions, not a prescription to inherit all current
JW behavior. Current JW contains rollback/recreation machinery. The proposed
architecture's failure contract remains no rollback/recovery guarantee; it does
not require porting that machinery into a generic cursor or transfer engine.

### Desired archive-derived composition

The desired assembly retains the native/data separation while opening the
materialization choice:

1. **Resolve native identity and options in JW.** Bind `A`, `W`, name and `D`.
   Decide colocation and transfer behavior before starting creation. Source
   validity and concurrent writers are premises, not a new audit protocol.
2. **Create receiving identity through JJ.** Native creation establishes the
   receiving `.jj`, registration and, when requested/supported, Git linkage.
   Ordinary materialization is available; suppressing it to prefill CoW data is
   a separate, feasibility-gated composition.
3. **Transfer selected data.** Generic components operate on admitted content
   only, with archive `.jj` and `.git` outside ordinary copy authority. Existing
   tracked-list cloning is a viable adapter route. Broader directory copying or
   generated control bytes would require explicit selection/production rules;
   they are not obtained by copying native metadata as generic files.
4. **Reconcile native materialization.** If donor cache adoption is used, JW
   coordinates that adoption and native convergence to `D`. Generic stat equality
   cannot certify a JJ file-state cache or Git index.
5. **Publish command result.** JW owns managed identity/bookmark/link outcomes;
   transfer owns its progress result. Failure may leave partial native and data
   state. No automatic rollback or serialized effects history is promised.

### Feasibility boundary

Current JW probes the executable's actual `workspace add --help` for `--colocate`
and verifies a Git backend with `git root` (`jj.rs:362–389`). Its diagnostic says
“generally 0.46+”; the probe, not a guessed release number, is authoritative. No
runtime was probed in this research. A local non-Git backend cannot provide this
Git result; an executable without the flag cannot use this native route.

Default-on colocation with native materialization is architecturally expressible
by the existing adapter. Default-on colocation **with preserved CoW behavior** is
unsettled: current mode selection rejects the combination, and the clone fallback
paths were written for JJ-only creation. Do not just remove that conflict and
assume the lifecycle composes.

The smallest discriminating experiment is one tiny archive with donor tree `S`
and different desired tree `D`: on an explicitly recorded JJ/Git/runtime/filesystem,
try native colocated sparse-empty creation, tracked prefill, donor `tree_state`
adoption, native validation and convergence to `D`. Inspect receiving checkout
identity, JJ tree/parent, Git worktree registration/HEAD/index/status and the
unchanged prefilled leaf's inode. This tests both correctness and whether the
intended prefill survives native convergence. It does not measure broad checkout
cost. If it fails, preserve the failure's exact stage as the reason this combined
route is unavailable, rather than substituting a hand-written Git topology.

## Scenario 3 — pause/resume assessment with generated contents

### An implemented component composition

The [cursor example](/examples/cursor/README.md) supplies a concrete assembly:

```text
bound trees + directory-summary/v1(label)
  → Cursor frames/tips
  → inspect_directory(NoVisitor)
  → reduce immediate observations into counts and children
  → postorder completion generator
  → logical summary.txt bytes + advanced Cursor
  → optional Snapshot persistence / next invocation
```

The actor supplies two real directory roots, a positive assessment budget `N` and
a label. The output is an advanced continuation plus invocation events containing
actual manufactured bytes. No generated file is installed into either tree.

The driver owns `Tip { logical, source, target }`, `Frame { phase, children,
next_child, totals, incomplete }`, counters, a possible blocked tip, and final
aggregate state (`examples/cursor/src/cursor.rs:107–182`). Tips carry optional
directory sides; at a directory/leaf collision the assessment visits the sole
directory side. This is assessment traversal, not decomposition of a coupled
filesystem replacement. The example rejects mapped coordinates: every present
side must coincide with its logical coordinate.

### Step, pause, retry and skip

1. A pending frame attempts one immediate directory assessment, including real
   directory validation for its present sides. Success stores counts and selected
   child tips and marks the frame assessed. Failure consumes one unit, leaves the
   frame pending and records its block; no partial immediate counts are added.
2. Assessed frames descend in native-name DFS order. After children finish, the
   compiled descriptor handler renders summary bytes and the frame folds its
   totals into its parent. Completion/push/pop transitions use no assessment
   units and drain after the last budgeted assessment.
3. At pause the active stack, remaining children, indices and aggregates are
   sufficient to continue. Old ancestors are not relisted and old events/bodies
   are not stored. A wide directory is still wide: `N` bounds attempts, not bytes,
   entries, latency or memory.
4. Resume retries a blocked pending tip. Explicit skip discards that scheduled
   subtree and immediately marks all active ancestors incomplete; it does not
   skip only one problematic file within the failed batch. Terminal resume needs
   no tree I/O.

`PlanWalk::next()` is not this step interface. It runs through clean directories
until an observed divergent batch is yielded, and comparison leaves one-sided
interiors opaque (`walk.rs:71–76,175–211`). Its private frames are neither public
construction inputs nor serializable state. The example therefore composes the
public immediate inspector with its own driver instead of replaying a walker
and discarding old results.

### Component-built continuation

The architectural construction boundary is **binding + traversal state + frozen
component configuration + each stateful component's continuation**. A generator
descriptor and its parameters are data selecting installed behavior, not saved
executable code. The example proves a single concrete descriptor composition; it
does not establish a general handler registry or select static versus dynamic
dispatch for the wider architecture.

The general rule is to save whatever affects future progression: pending tips,
phase/child position, aggregates and component-owned incremental state. Borrowed
dirents, open handles, active worker jobs, `Metadata` and staging leases are
runtime resources, not continuation data. Components must either reach a quiet
boundary where these can be released/reconstructed or supply an explicit owned
representation. The sequential example pauses after immediate assessment and
completion transitions; a parallel driver would have to join its active epoch
before publishing an equivalent quiet boundary.

Serialization is optional: the same in-memory driver can continue without a
codec. The actual example uses kopacetic snapshots and owned reconstruction;
its Unix path encoding and descriptor validation are concrete codec/application
choices. [The implementation report](/design/cursor/implementation0.gpt61sxh.md)
records twelve focused passing tests, including multi-process continuation and
retry/skip. Those checks were not rerun here.

### Extending generated output to filesystem work

Generated `summary.txt` is already real byte production, but it is a logical
output event. Current `Names` forbids inserting/renaming slots, current
`Operation` cannot fabricate observations, and `Action::InstallLeaf` requires an
actual different/absent source leaf. A generated file that exists in neither
listing therefore cannot be expressed through the existing visitor action alone
(`visitor.rs:150–152,247–294,437–468`).

To materialize generated output, compose an **explicit producer** with an
**explicit output installer**. The producer returns destination-relative
coordinate, bytes or a content recipe, and intended metadata. The installer
observes the actual destination and applies a declared collision policy. A
generated entry must retain generated provenance; it must not pretend to be an
observed source entry. Output path reservation and parent creation belong at
this installation boundary. Whether that uses an extended plan vocabulary or a
separate consumer remains open.

For the concrete summary scenario, the clearest initial extension writes to a
separate output root, with a stable mapping from assessed directory to summary
destination. This avoids outputs entering later input assessments. Writing into
the receiving tree is possible only with an explicit rule for collisions with
copied files, output exclusion from traversal, and replacement intent. Neither
choice is implemented by the example.

Once effects are added, an assessment cursor alone is insufficient to pause
inside recursive sync work. `execute_batch` can recursively consume an entire
source-only subtree before returning. A resumable application driver needs its
own pending application/child/completion phases, or deliberately accepts that
whole recursive operation as its indivisible pause unit. Generated postorder
output likewise needs a completion phase if generation/installation can fail
and remain retryable. These are continuation states, not an effects ledger.

Cursor publication and output delivery are not jointly transactional. The example
publishes the cursor before stdout; output can be lost, and replaying an older
cursor can repeat output. Adding filesystem materialization does not change the
premise: retry reattempts declared work against actual state, skip omits remaining
work and marks coverage incomplete, and neither undoes already performed effects.

## Highest-value unresolved decisions

1. **Colocation plus prefill:** can native sparse-empty colocated creation and
   tree-state adoption converge both JJ and Git while retaining useful CoW work?
   The tiny versioned experiment above discriminates this before changing defaults.
2. **Generated installation ownership:** choose the concrete producer/installer
   seam, collision rules and metadata parameters. A tiny generated destination
   absent from both input listings, then colliding with an existing target file,
   distinguishes a genuine mechanism from a visitor-only workaround.
3. **Application pause granularity:** must `N=1` stop within a large source-only
   subtree, or is recursive application one unit? A two-level source-only branch
   with a deliberately failing child exposes the necessary continuation phases.
4. **Component continuation contract:** decide which components are supplied at
   construction and which carry owned state/configuration through serialization.
   A second parameterized producer with different accumulator needs tests this
   seam more effectively than declaring a universal dispatch framework first.

These questions preserve the working compositions: ordinary copying already has
an inspector/selector/applier path; native workspace creation already owns
repository identity; assessment already has a real continuation example. The
extensions concern how those components compose beyond their implemented bounds.
