# Architecture: early stakes

This is the first concrete statement of where I expect the architecture to land.
The statements below are **bets about the intended system**, with explicit places
where evidence can change them. They are not claims that every mechanism exists
today. The existing root specification continues to describe the shipped core.

Independent researchers receive the [question brief](../roadmap/brief0.gpt6a.md),
their scoped ticket and factual sources. They do not read, search, cite or evaluate
this document while producing their independent findings. After their outputs
are committed, `diffdir-tree-compare` brings the accounts together. Preserve this
version so that later reasoning is compared with the actual early expectation.

## Purpose and principal scenario

The system composes **tree observation, selected work, traversal and application**.
Its ordinary job is to produce a receiving tree from source contents while retaining
the destination-specific state chosen by the caller. Git and JJ are consumer
adapters, not the generic explanation for copying files.

The principal JW source is the **JJ archive**. New or existing receiving workspaces
have their own identity. An existing registered workspace as source is a useful
extension to explore, not a reason to obscure the archive scenario behind an
assumption that every source is interchangeable.

The desired `jw add` experience includes a working Git checkout alongside JJ by
default, with `--no-colocate` as an opt-out. The bet is that native JJ Git colocation
can supply that topology while we preserve useful archive-copy performance. This
remains conditional on what JJ/Git can actually support.

## Components and flow

1. **Entry providers** supply logical tree entries. Physical directory enumeration
   is one provider; generated bytes or a generator recipe can supply another.
   Origin stays explicit. Logical output coordinates need not equal source paths.
2. **Observation** acquires the facts needed by the current assessment and chosen
   operation. Listing facts, comparison keys and content-transfer attributes have
   different costs. An add/change/remove view remains useful to reporting callers.
3. **Assessment** selects work and child traversal context. It does not mutate an
   observed fact to obtain a different permission to act. Application attributes
   can retain initial classification or a domain-specific mapping.
4. **Actions and handlers** express and perform work. A descriptor identifies a
   handler and its parameter shape/version; optional attributes travel alongside.
   Handlers can expand into child tasks or produce new logical entries.
5. **The driver** advances the ordered work, owns active frames and folds child
   results. Existing pure visitor inspection can remain a building block. Ordered
   state does not hide inside callbacks that may run speculatively.
6. **The cursor** is the portable description of unfinished iteration: roots/tips,
   active frames, remaining selected work, context and required accumulators.
   Runtime code and open handles are supplied again when it is reconstructed.
7. **Consumer adapters** define concrete filesystem/native metadata behavior.
   They use generic retention, generation and mapping capabilities where those fit.

The flow is:

```text
entry origin → needed observations → selected action + child context
            → handler/child steps → entity finalization → yielded result
```

This is a composition of useful mechanisms. It does not require every read-only
comparison consumer to instantiate a dispatcher or persistence backend.

## Completion, construction and continuation

Completed entity results are naturally post-order: the directory is returned
after its children have been processed. Effects can still happen on entry or exit
as required. A directory may be created before its children and finalized after
them. A small accumulator can replace retaining all child results.

A builder assembles a cursor/driver from components. It exposes fresh creation
and construction from captured parts without making either depend on a hidden
global context. The architecture separates portable position/state from runtime
observer and handler implementations. The exact Rust generic/trait surface is
still a bet to test through the next walking specimen.

Stepping and completed results are different units. One step may yield nothing;
the last child can finish several ancestors. The initial CLI bounds attempted
directory assessments. Later consumers may need a finer boundary inside a wide
directory or a whole-tree action.

Failure leaves what happened. A saved position enables continued iteration,
retry or skip; it is not an effects log or an exactly-once receipt. A stale cursor
may revisit work. Concurrency and locking remain out-of-band concerns.

## Actions and generated contents

The fixed filesystem enum remains a useful built-in vocabulary. My bet is that
an extensible descriptor envelope avoids multiplying variants for every consumer:

```text
handler identity + payload version + parameters + optional attributes
```

Typed parameters are desirable for known handlers; an extensible KV payload can
serve application-defined ones. The dispatcher supplies executable meaning.
Serializable parameters do not serialize executable Rust code.

Copy-tree, retain, remove, write-generated and mapped-output behaviors should
compose with child traversal. A generator can use an accumulator and emit bytes
when its entity completes. The same-destination rule must be explicit when a
physical entry and generated output name the same location.

A physical pair can compare equal and still require generated work. Therefore
the execution driver's output is not gated solely by a nonempty physical diff.

## Work avoidance

At a source-only subtree, the driver already knows there is no destination tree
to compare. It changes the recurse tip to a simpler source-copy context. If every
descendant follows the same rule, general assessment stops there; only necessary
source observation and installation continue. If exceptions remain, the context
carries those residual rules.

The bet is that inherited modes yield more than adding faster callbacks to an
unchanged generic comparison loop. Preserve can end traversal entirely. A known
file list can avoid unrelated discovery. An unchanged leaf can avoid transfer.
Whole-tree copying still normally enumerates and installs its entries.

Source-to-many reuse is a later composition of the same observation/lifetime
model. A permanent full-tree catalog is not assumed necessary.

## Names and persisted representation

The expected useful optimization is packed/retained name storage with borrowed
`OsStr`/`Path` views and delayed full-path construction. The current native reader
allocates and clones names; Unix byte-to-borrowed-path conversion already needs
no allocation. Buffer ownership across iteration and sorting is the actual issue.

Unsafe or native parsing is a legitimate implementation option if it removes
meaningful work. A variable-length dirent is not an owning `PathBuf`; a raw cast
does not provide the missing ownership or lifetime.

Kopacetic-rkyv is the initial cursor codec because the first specimen demonstrates
working Facet-state roundtrips. It archives reflected path rows and reconstructs
owned state. My bet is that it is useful for structured extensible state, while a
native rkyv or packed representation may be preferable if real cursor costs justify
the specialization. Neither speed nor minimum representation size is assumed.

## Native metadata: archive and receiving workspace

The generic transfer does not copy the archive's `.jj`/`.git` blindly into a
receiving workspace. Existing destination identity is retained; new identity and
Git worktree registration are supplied by the native creation path. The iterator
can suppress native regions or consume explicitly supplied/generated entries.

Archive Git backing state, receiving `.git` gitfile, per-worktree administration,
shared common Git directory and JJ workspace binding have distinct owners. The
native adapter states the actual layout for the supported archive/workspace forms.
The archive is a source role/location, not a claim that its `.git` must have one
universal physical shape.

Preserving target `.jj` does not itself advance its revision. If the requested
outcome is revision advancement, the JJ adapter performs that operation. If the
requested outcome is only copying, graph manipulation need not be invented.

For Git colocation the present evidence is limited: installed JJ exposes
`workspace add --colocate` and `--no-colocate`; JW already invokes that capability.
JW's current creation policy makes CoW and colocation exclusive. That is a JW
implementation fact, not yet proof of a fundamental JJ restriction or proof that
the combination will work.

Research may find that default colocation is unavailable for a required backend,
incompatible with useful native state/materialization behavior, or unacceptably
expensive. A sound return explains the precise reason and relevant versions,
then offers the smallest workable choice. It need not force the preferred default
through an unsupported composition. Workspace-as-source research likewise tests
which archive assumptions survive and which must be explicit.

## Bets to compare with the research

| Bet | Evidence that could change it |
| --- | --- |
| Existing observation/visitor machinery can feed a small stateful driver | Concrete ownership or control-flow requirements force a different shared boundary |
| Component construction and portable parts can remain cleanly separated | Required context cannot be restored without material runtime coupling |
| Extensible descriptors plus built-in actions suffice | Real handlers require a substantially different result/composition algebra |
| Post-order completion and small accumulators are useful | Required consumers need earlier entity publication or retained child information |
| Inherited subtree modes remove worthwhile assessment work | Measured policy work is negligible or the necessary exceptions retain nearly all cost |
| Retained names/offsets beat repeated owned-name construction | Lifetime, sorting or persistence cost erases the allocation saving |
| Kopacetic fits useful cursor payloads | Actual archive/reconstruction costs or supported shapes make it a poor fit |
| Native Git colocation can be the jw add default with useful copying | Required JJ/Git behavior or acceptable costs make that combination unavailable |
| A registered workspace can be a useful source | Its identity, installed contents or native topology breaks required source assumptions |
